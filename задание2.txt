Самостоятельная работа: Разработка REST API для системы «Общежитие»
Цель задания: Разработать серверную часть (REST API) для управления структурой общежития, студентами и заселением, реализовав две роли доступа с разным уровнем привилегий.
1. Архитектура базы данных и сущности
Вам необходимо спроектировать и создать миграции для следующих таблиц:
rooms (Комнаты):
id
room_number (номер комнаты, строка или число, уникальное)
floor (этаж, целое число)
capacity (максимальное количество мест, например: 2, 3 или 4)
students (Студенты):
id
first_name (имя)
last_name (фамилия)
room_id (внешний ключ, указывает на комнату. Может быть NULL, если студент еще не заселен)
users (Пользователи системы / Персонал):
Стандартная таблица пользователей Laravel, но с обязательным текстовым или enum-полем 
role.
Допустимые роли: admin (Администратор) и warden (Смотритель).
2. Аутентификация и Роли
Аутентификация должна быть реализована на базе Laravel Sanctum (выдача токенов при логине).
Разграничение прав должно работать через кастомное Middleware 
(например, CheckRole), которое вы должны написать самостоятельно 
и зарегистрировать в bootstrap/app.php.
Матрица прав доступа:
Роль warden (Смотритель): имеет право выполнять только GETзапросы 
(просмотр комнат, просмотр списка студентов).
Роль admin (Администратор): имеет полные права (GET, POST, PUT, DELETE) 
на все ресурсы системы.
3. Требования к Эндпоинтам (Маршрутам)
Все роуты, кроме авторизации, должны быть защищены middleware auth:sanctum.
Группа Аутентификации:
POST /api/login — публичный роут. Принимает email и password, возвращает токен.
Группа «Комнаты» (/api/rooms):
GET /api/rooms — вывод всех комнат с количеством фактически заселенных в них студентов (используйте withCount).
POST /api/rooms — создание новой комнаты (Доступ: только admin).
DELETE /api/rooms/{id} — удаление комнаты (Доступ: только admin).
Группа «Студенты» (/api/students):
GET /api/students — список всех студентов. Рядом с каждым студентом должен выводиться объект комнаты, в которой он живет, если она привязана (with('room')).
POST /api/students — добавление нового студента в систему (без заселения в комнату, room_id по умолчанию null). (Доступ: только admin).
PUT /api/students/{id}/settle — заселение студента в комнату или переселение. Принимает room_id. (Доступ: только admin).
4. Бизнес-логика и Валидация (Критические точки)
При реализации метода заселения студента (PUT /api/students/{id}/settle) необходимо запрограммировать следующие проверки в контроллере или Form Request:
Выбранная комната (room_id) должна существовать в базе данных.
Проверка на перенаселение: Система должна подсчитать, сколько студентов уже живет 
в этой комнате. 
Если текущее количество жильцов равно или превышает capacity (вместимость)
комнаты, 
сервер должен заблокировать запрос и вернуть ошибку со статусом 
422 Unprocessable Entity 
и сообщением: "В этой комнате больше нет свободных мест".
